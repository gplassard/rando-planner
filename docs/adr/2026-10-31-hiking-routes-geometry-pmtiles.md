# ADR 2026-10-31 — Embed full hiking route geometry as PMTiles

## Status

Accepted (implemented on `feat/hiking-routes-geometry`)

## Context

The app currently displays hiking routes as **bounding-box rectangles** built from
`data/small_database.json` (id, name, from, to, bbox — 8.7 MB, bundled into the JS).
The complete trail geometry is only present in the raw magOSM WFS extract
(`data/raw/hiking_routes.geojson`, gitignored): **46 176 LineString/MultiLineString
features, ~290 MB of GeoJSON** covering France.

Notion task: *"Embarquer la géométrie complète des sentiers (trancher le format :
GeoJSON / PMTiles / FlatGeobuf)"* — embed the full geometry and decide the format.

Constraints:

- The site is **static** (GitHub Pages, base `/rando-planner/`): no server-side
  filtering, but HTTP `Range` requests are supported.
- Rendering stack is **Leaflet** + react-leaflet.
- The dataset is refreshed **weekly in CI** (`update-data` workflow runs
  `pnpm run data` on `ubuntu-latest` and commits `data/`).
- Files committed to git must stay well under 100 MB.
- 46k routes rendered as individual Leaflet SVG nodes (current rectangle approach)
  is already a DOM bottleneck.

## Options considered

### 1. GeoJSON (single bundled file)

- ✅ Trivially compatible with react-leaflet's `<GeoJSON>`.
- ❌ ~290 MB raw; even minified/rounded it is far above the 100 MB git limit and
  would destroy initial page load (currently 8.7 MB of metadata alone is bundled).
- ❌ No zoom-adaptive simplification: every route is parsed and drawn at every zoom.
- Splitting into per-grid-cell GeoJSON files would fix loading but keeps the
  no-simplification problem and adds ~300 MB to the repository.

### 2. FlatGeobuf (.fgb)

- ✅ Single static file, HTTP range requests + spatial index; writable in pure
  Node (`flatgeobuf` npm package), no extra CI tooling.
- ❌ Not tiled: a client must deserialize **every feature intersecting the current
  viewport**. At low zoom over France that is the whole dataset (~290 MB decoded in
  browser memory). Mitigating with a zoom threshold means re-implementing what tiles
  give for free.
- ❌ No zoom-level simplification; weak Leaflet integration (OpenLayers-oriented).

### 3. PMTiles (vector tiles) — chosen

- ✅ Single static file served over HTTP range requests (supported by GitHub Pages).
- ✅ Client only fetches tiles in the viewport; zoom-adaptive simplification and
  feature dropping keep tiles small and rendering fast (one canvas layer instead of
  46k SVG nodes).
- ✅ Natural fit with Leaflet via `protomaps-leaflet` (canvas vector-tile layer).
- ✅ Generatable in CI: `tippecanoe -o out.pmtiles` (Ubuntu `universe` package,
  version ≥ 2.26 writes `.pmtiles` directly).
- ⚠️ Requires the `tippecanoe` binary in the data pipeline
  (`sudo apt-get install -y tippecanoe` on Ubuntu).

## Decision

Embed the complete hiking route geometry as a **single PMTiles archive**,
`data/prepared/hiking-routes.pmtiles`, generated by the data pipeline with
`tippecanoe` from `data/raw/hiking_routes.geojson`:

```
tippecanoe -f -o data/prepared/hiking-routes.pmtiles \
  -l hiking_routes -z 13 -b 8 \
  --drop-densest-as-needed --drop-smallest-as-needed \
  -y name -y from -y to \
  data/raw/hiking_routes.geojson
```

- Layer name `hiking_routes`, max zoom 13 (beyond that OSM basemap detail dominates)
  and small buffer, which keeps the archive around 50 MB — comfortably under git's
  100 MB file limit. Only `name` / `from` / `to` attributes are kept to bound tile size.
- The archive is committed (like `data/prepared/stations.json`) and refreshed weekly
  by the `update-data` workflow; the app loads it with a `?url` import so Vite emits
  it into `dist/assets`.
- The map renders trails as a protomaps-leaflet canvas layer
  (`LineSymbolizer`) instead of one `<Rectangle>` per route; the 8.7 MB
  `small_database.json` is no longer bundled.

## Consequences

- Positive: real trail geometry at every zoom, much smaller and faster map rendering,
  no 290 MB GeoJSON in the repo, route names available in tiles for future tooltips.
- Negative: `pnpm run data` now requires `tippecanoe` (documented in `AGENTS.md`,
  installed in the `update-data` workflow); the `.pmtiles` archive is a binary
  artifact (~tens of MB) committed to git.
- `data/small_database.json` / `data/small.json` are still produced by the pipeline
  as metadata products but are no longer imported by the app.
